🏠 3. Resident Dashboard — Overview Module
Derived from F-02, F-03, F-11, F-12, F-13
REQ-01Community Income tile must respond to period filter
DefectHigh Priority

The Community Income (RD-05) tile always shows the same static figure regardless of the selected date period. This breaks user trust and makes period-based financial analysis impossible.

Community Income figure does not change when switching between FY, monthly, or custom range filters. Sub-text "₹0 from hall rental, signage, events" appears as placeholder text even when actual data exists.

Tile and all sub-breakdowns recalculate on every period filter change. When no income exists for the selected period, display: "No community income recorded for this period."

Management committee reviews income on FY and monthly basis. A stagnant figure invalidates the entire dashboard's credibility during stakeholder presentations.

Wire the Community Income component to consume sliceMonthly from usePeriod(), consistent with all other charts. Remove all hardcoded values. Add empty-state guard with period-aware message.

⚠ Before
Community Income = ₹1,50,000 regardless of FY / Month selected. Sub-text "₹0 from hall rental..." always visible even when real data exists.
✓ After
Community Income = ₹38,500 for Apr–Jul 2026 (dynamically computed). If nil: "No community income recorded for Apr–Jul 2026."
REQ-02Redesign Overview with 4-tile layout: Expense, Income, Vendors, and Trend
EnhancementMedium Priority

Overview has only 2 charts. Vendor-level spend and Income trend are absent. The 2-chart layout underuses screen space and provides an incomplete financial picture.

Four equal tiles in a responsive 2×2 grid:
1. Top 5 Expense Categories (with drill-down)
2. Community Income Sources (top 5, with drill-down, same format as expense)
3. Top 5 Vendors by Expense (new, with drill-down)
4. Monthly Collection vs Expense + Outstanding trend

Rename "Non-maintenance income" to "Community Income Sources" matching expense section style. Remove sub-description "₹0 from hall rental..." Replace with actual dynamic data or proper empty state.

Clicking any bar or count within a chart tile opens an inline drill-down table. Chart/Number toggle must work for all 4 tiles. Number view shows a formatted ranked table.

Vendor visibility supports payment authorization governance. Income at the same granularity as expense gives residents a balanced view. Adding the Income trend completes the financial picture on the landing screen without requiring navigation.

REQ-03Add Defaulter visibility to Overview (RD-03 chart + standalone tile)
EnhancementHigh Priority

Residents who have not paid maintenance ("defaulters") represent lost revenue and are a primary concern for the committee. Zero dashboards currently show defaulter count, outstanding amount, or trend.

Add a third series to the Collection vs Expense chart representing "Outstanding Maintenance" (billed − collected). This shows the monthly collection gap visually without replacing existing series.

Add a dedicated card showing: total units in arrears, outstanding amount for selected period, and top 5 defaulting flats (admin-configurable visibility). Can reside within or alongside the Community Income area.

Requires: (a) Expected maintenance amount per period (units × rate), (b) Actual collected, (c) Derived: outstanding = expected − collected. If billing amount not in DB, add a community-level "monthly maintenance rate" config field.

Phase 1: Add outstanding series to RD-03 using existing collection data + configurable expected amount. Phase 2: Full Defaulters module (admin-only) with flat-level arrears list once billing data is available.

REQ-04Split or annotate "Utilities" expense category
EnhancementMedium Priority

"Utilities" may aggregate BESCOM A/B/E/G blocks, water supply, and other sub-categories, making it impossible to see per-utility contribution to overall expense.

Option A (Preferred): Split into distinct sub-categories (Electricity — Block-wise, Water Supply, etc.) visible in drill-down.
Option B: Add expandable row under Utilities showing vendor/sub-category breakdown inline.

Verify BESCOM sub-categories exist as separate line items in ETL output. If currently merged, a data mapping change is required before UI work begins.

BESCOM blocks have separate meters and tariff structures. Per-utility visibility is needed to validate charges and identify consumption anomalies.

💰 4. Resident Dashboard — Income Visibility
Derived from F-01, F-04, F-06, F-08
REQ-05RD-31: Replace "Income left" with "Surplus / Deficit"
UX / LabelLow Priority

Net amount after expenses is labelled "Income left" — informal and ambiguous.

Dynamically display "Surplus" when the value is positive, and "Deficit" when negative. This is standard RWA financial terminology understood by residents and auditors alike.

REQ-06RD-32: Add Maintenance-only chart with Defaulter overlay
EnhancementHigh Priority

RD-32 shows a general income trend. Stakeholders require a dedicated monthly bar chart for Maintenance collections specifically, overlaid with defaulter amounts to visualize collection efficiency.

Grouped/stacked monthly bar chart:
• Bar 1: Maintenance Collected (green)
• Bar 2: Outstanding / Defaulted (red/amber)
Tooltip on hover: unit count in arrears + amount due.

Requires expected billing amount per month. If not currently captured, a community "monthly maintenance rate" configuration field must be added.

REQ-03 data model (defaulter schema). Phase 2 delivery after billing config is available.

REQ-07Correct "Tax as revenue" — GST collections are liabilities, not income
Defect / DataHigh Priority

CGST Output and SGST Output collected on community services are shown in the Income module as revenue. Tax collected is a liability payable to the government — not community income.

Either: (a) Exclude CGST/SGST from income total, showing separately as "Tax Collected (Liability)", or (b) Present income figure "Ex-Tax" prominently with tax collected as a footnote. Either way, the income total must not include tax.

Including tax in income overstates revenue and creates compliance risk. This must be corrected before any financial report is shared with residents, auditors, or the registrar.

REQ-08Validate Facility Rental income figure (₹1.5L for 6 months)
Data ValidationMedium Priority

Facility rental income shows ₹1,50,000 for 6 months in the income breakdown. Stakeholder has raised this as a potential data anomaly that needs reconciliation against actual bookings.

Reconcile against booking / receipt records outside the application. If figure is correct, no change needed. If incorrect, fix ETL mapping. Optionally add a z-score based anomaly flag in ETL pipeline for large income entries.

📈 5. Resident Dashboard — Cash Flow & Balance
Derived from F-03, F-05
REQ-09RD-20: Remove "Within Budget" — replace with factual expense-to-collection label
DefectHigh Priority

RD-20 displays "Within Budget ✓" when expense is below collection. No budget module exists in the application. This label is factually incorrect and will cause stakeholder confusion during financial reviews and audits.

Replace with accurate comparison label:
• "Expense below collection" (expense < collection)
• "Expense exceeds collection" (expense > collection)
Or show numeric surplus/deficit value without a qualitative badge.

⚠ Before
Badge: "Within Budget ✓" — implies an approved budget approval process exists. Misleading during audit reviews.
✓ After
Label: "Expense below collection" OR show "Surplus ₹42,000" — factually accurate, no false budget implication.
REQ-10RD-42: Fix negative opening balance in 6-month view
DefectHigh Priority

The balance strip shows a negative opening balance when "Last 6 months" is selected. A negative opening balance is financially incorrect for a housing society fund and signals a data aggregation error.

1. Prior period ETL data is incomplete, causing incorrect opening balance computation.
2. Refund/adjustment transactions may be double-counted in balance calculations.

Opening balance must reflect actual fund balance at start of selected period. If data is insufficient, show "N/A" with tooltip explaining the data gap rather than displaying a negative number.

1. Audit the balance strip SQL for the selected period.
2. Verify ETL imports cover contiguous months.
3. Add data-completeness warning if months are missing.
4. Guard against negative opening balance with a validation flag.

🔧 6. Admin Dashboards — Analytics
Derived from F-09, F-10
REQ-11RD-10: Sort expense drill-down descending by default
UX / SortingMedium Priority

Expense drill-down lists categories in an arbitrary order. The Overview already shows Top-5 descending but the full list in drill-down is not sorted, making it harder to locate largest expense items.

Default sort: descending by total amount for the selected period. Consistent with the Overview top-5 ordering in descending order.

REQ-12RD-10: Rename "Accounting Adjustment" to a descriptive label
UX / LabelMedium Priority

"Accounting Adjustment" is a vague catch-all that gives residents and committee members no context about what transactions are grouped here. It consistently raises questions during reviews.

Rename to a specific, meaningful label such as "Adjustments & Corrections" or "Prior Period Entries". Add a tooltip or help icon with a brief description of qualifying transactions.

Ensure this rename is applied consistently across all drill-down views, expense category selectors, and ETL category mappings. Coordinate with data/ETL team to avoid breaking existing category filters.

REQ-13Annotate "Recreation & Wellness" with sub-item description
UX / ClarityLow Priority

Residents are unclear about what is included under "Recreation & Wellness" in the expense breakdown, raising the same questions every review cycle.

Add a category description visible as a tooltip on hover, or as a sub-header in drill-down, listing contributing vendor types (e.g. Swimming Pool Services, Fitness Trainer, Club House Operations).

⚙️ 7. Cross-Cutting — UI Consistency
Derived from F-14
REQ-14Chart ↔ Number view toggle must function on ALL dashboard pages
DefectHigh Priority

The Chart / Number toggle in the header bar is non-functional or hidden on multiple Admin and Resident pages. Toggling to "Number" has no effect, or the toggle itself is absent.

On every dashboard page, "Number" view replaces charts with a formatted ranked data table showing the same data. "Chart" view restores visuals. Behaviour must be identical across: RD Overview, RD Income, RD Cashflow, RD Balance, AD Alerts, AD Collections, AD Income, AD Actions, AD Vendors.

Components check the view context from usePeriod() but not all chart components branch on this value. Some pages pass showViewToggle={false} to PortalShell, hiding the toggle entirely without a table fallback.

1. Audit all route components for showViewToggle usage.
2. Ensure every chart-bearing page has a parallel table / number render path.
3. Create a shared NumberTable component to standardize this.
4. Regression-test the toggle on all 9+ affected pages before Phase 3 work begins.

🔎 11. Gap & Opportunity Analysis
Missing capabilities and improvement areas not directly captured in submitted feedback
No Maintenance Billing Module

Collections are recorded but no expected billing per unit exists. Without this, defaulter detection, collection efficiency %, and expected vs actual reporting cannot be computed. A configurable billing schedule per community is a foundational gap.

No Budget Planning Feature

The "Within Budget" label implies budget tracking exists but it does not. Until a budget module is built, all budget-related language must be removed. Long-term, a budget input and variance dashboard would provide genuine financial planning capability.

Chart/Number Toggle Incomplete

Multiple pages either suppress the toggle or lack the table fallback. A shared NumberTableView component standardizing this across all 9+ pages would reduce maintenance effort and ensure consistent UX.

Income Category Classification Gap

GST/Tax collections appear in income totals. A clear ETL-level separation of "Operating Income" vs "Tax Collected (Liability)" is needed to ensure accurate financial reporting.

Vendor Granularity Missing from Overview

Expense categories are shown but not vendor-level. Vendors are the actual payees for most expenses. Vendor analytics directly support payment authorization governance and committee oversight.

Mobile Drill-Down UX

Drill-down tables and charts may have small tap targets and horizontal scroll issues on mobile. The interactive experience should be tested and optimized across small-screen devices.

Data Completeness Indicator

Users have no way to know if data shown for a period is complete or if ETL imports are missing months. A data freshness / completeness flag on each dashboard would significantly improve stakeholder trust.

Extended Export for Audit Workflows

Current CSV export covers monthly totals only. A full export per period including income classification, vendor breakdown, and balance reconciliation would support external auditor and management committee review.

⚠️ 12. Risks & Dependencies
Key considerations for technical planning and scope management

Technical Risks

  • REQ-03 & REQ-06 require a new DB schema for expected billing amounts. A backend migration and community admin configuration step is needed before data populates.
  • REQ-10 (negative opening balance) may require backfilling ETL imports for prior months if transaction history is incomplete. Data availability must be confirmed before scope is estimated.
  • REQ-07 (tax reclassification) touches ETL income categorization. Retroactive category mapping changes may alter historical income totals in past-period filters, affecting FY comparisons.
  • Removal of retainSearchParams (already done) may break period state persistence on drill-down back-navigation. Regression test required.

Functional Dependencies

  • REQ-03 & REQ-06 depend on a "Monthly maintenance amount" configuration setting added to the community settings page.
  • REQ-04 (Utilities split) depends on BESCOM sub-categories existing as separate ETL line items. Confirm with data team before scheduling.
  • REQ-08 (Facility rental validation) requires access to original booking records outside the application.
  • REQ-12 (rename Accounting Adjustment) must be coordinated with ETL team to keep imports consistent post-rename.
  • REQ-14 (toggle audit) must be completed before new Phase 3 chart features are added to avoid compounding breakage across pages.
